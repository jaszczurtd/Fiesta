# ECU MISRA Deviation Register

This register tracks active MISRA deviations, validated tool false positives, and intentionally deferred findings for `src/ECU`.

Rules:

- Every active suppression in `suppressions.txt` must have a matching row here.
- Prefer fixing code before documenting a deviation.
- Required or Mandatory findings must not be treated as closed without an explicit rationale and disposition.
- When a deviation is removed, keep the historical row and mark it as closed instead of deleting it silently.

Column meanings:

- `ID`: local tracking identifier.
- `Rule`: MISRA rule ID, or `n/a` for process/bootstrap entries.
- `Scope`: affected file or subsystem.
- `Type`: `tool-fp`, `accepted-deviation`, `pending-fix`, or `bootstrap`.
- `Status`: `open`, `planned`, `closed`, or `none`.
- `Rationale`: short justification.
- `Suppression`: matching entry in `suppressions.txt`, or `none`.

| DR-007 | 19.2 | `src/ECU/vp37_snapshot.c`: the float bit patterns of the published VP37 status and the word view of the telemetry staging buffer | accepted-deviation | open | Advisory. The control core shares its state with the other core only as `uint32_t` words accessed with atomics, which removes the data race of a plain copy (memory orders: DR-008). A float field and a struct have to become words and back; C offers `memcpy`, which breaks Required rule 21.15 (incompatible pointer types), or a union, whose member reads reinterpret the stored representation as C11 6.5.2.3 defines. A `_Static_assert` next to the float conversion stops the build unless `float` and `uint32_t` have the same size. The status words carry no padding: they are built from the four fields, not from a struct. The telemetry words do carry the padding bytes of `VP37Telemetry`, and their content does not matter. The staging union has static storage, so every byte is zero before the first publication (C11 6.7.9p10); after member stores the padding bytes take unspecified values (6.2.6.1p6), which C11 counts among indeterminate values (3.19.2). The words are read as `uint32_t`, an exact-width type with no padding bits and so no trap representation (7.20.1.1), so such a read yields some valid value and is not undefined behaviour. The reader writes those bytes only into the padding of its own `VP37Telemetry`, which no code reads, because members are accessed by name. The unions are local to this unit and the host tests read every value back exactly, including under ThreadSanitizer. Decided 2026-09-30. | `misra-c2012-19.2:*vp37_snapshot.c` |
| DR-008 | 21.25 (Amendment 4) | JaszczurHAL `HAL_ATOMIC_*` with relaxed, acquire, release or acquire-release order in `src/ECU/vp37_snapshot.c` (publication of the VP37 snapshot), `src/ECU/vp37_telemetry.c` (hand-over of the bench trace buffer) and `src/ECU/tests_helpers.c` (console line queue, configurator request, contact time and session flag, test parameters) | accepted-deviation | open | The rule asks for sequentially consistent order in the `<stdatomic.h>` synchronization functions. These units use the GCC `__atomic` builtins behind the HAL macros, not the library functions, but the same concern applies, so the choice is recorded here. Snapshot: a sequence lock with one writer, as in Boehm, "Can seqlocks get along with programming language memory models?" (2012): the writer stores the odd counter, issues a release fence, stores the data words relaxed and publishes the even counter with release; the reader loads the counter with acquire, the data words relaxed, issues an acquire fence and reloads the counter. A copy is accepted only when both counter reads are the same even value, so it holds one whole publication. Sequentially consistent data words would put barriers around each of about 310 word stores in every 5 ms control step on the Cortex-M0+, which has no store-release instruction, without changing the result. Trace buffer and test-layer values: one core hands a buffer or a value to the other (message passing); each side's plain accesses come before its release store and after the other side's acquire load, which is exactly what acquire/release orders. No algorithm in these units depends on the order of a store and a later load of a different variable, the only case sequential consistency adds. Evidence: the host tests of the snapshot run under ThreadSanitizer and with interleaved publications, and a plain copy in place of the atomic words is reported as a race; they run on x86, whose hardware ordering is stronger than required, so the ordering on the RP2040 rests on the C11 model above, which the compiler implements with `dmb`. cppcheck 2.13 does not check Amendment 4 rules; this row records the decision. Decided 2026-09-30. | none |
